# Prime RLM RLVR Research Workspace

This repository is the working codebase for a thesis project on training
recursive language-model agents to decompose tasks, delegate sub-problems, use a
local REPL, verify evidence, and synthesize final answers.

The central research question is:

> Can a smaller trainable RLM learn useful orchestration behavior from RLVR and
> teacher traces, especially when plain sub-LLM calls are offloaded to API
> providers so GPU time is reserved for the trainable policy?

The current stack trains `Qwen/Qwen3-4B-Instruct-2507` with Prime-RL on
self-managed GPU pods. Root turns and recursive RLM child turns stay on the
local vLLM/Prime training model and remain trainable. Plain `llm_query` and
`llm_query_batched` subcalls are non-trainable trace/cost segments and are
routed to Vertex Gemini Flash-Lite in the active configs.

## Environment Design

`rlm_rlvr` is a multi-turn environment. Each rollout gives the model a question
and context, then the model writes Python in fenced `repl` blocks. The REPL can
inspect the `context` variable, call external one-shot LLMs, launch recursive RLM
children, and print intermediate results for the next turn.

Important runtime behavior:

- Root turns are generated by the local Prime/vLLM policy and are trainable.
- Recursive `rlm_query*` child turns are also generated by the local policy and
  are trainable.
- Plain `llm_query*` calls are external non-trainable subcalls.
- Plain subcalls still appear in traces and cost accounting because they are
  behavioral evidence and cost signals.
- Plain subcalls can use OpenAI-compatible providers or Vertex Gemini.
- Active configs use Vertex for plain subcalls and judge calls.
- `llm_query_batched` remains concurrent. Inside a rollout process it fans out
  subcalls through a thread pool.
- `rlm_query_batched` executes recursive child RLM calls serially by default,
  because each child can run a local REPL and the local REPL temporarily mutates
  process-global cwd/stdout/stderr. Set `recursive_rlm_batch_mode = "thread"`
  only for explicit experiments where that hazard is acceptable.
- Trace-generation can run multiple rollout workers safely with
  `worker_backend = "process"`, because the local REPL mutates process-global
  state such as cwd/stdout/stderr during execution.

The model is expected to finish with either a literal final answer or a REPL
variable final:

- `FINAL(actual literal answer)` is parsed as text outside a REPL block. It is
  not a Python function and does not evaluate expressions.
- `FINAL_VAR("answer")` is a Python REPL helper and should be used inside a
  `repl` block when the answer already lives in a Python variable.

Do not use expression finals such as `FINAL(json.dumps(answer))` or
`FINAL(answer)`. Those teach the wrong protocol because `FINAL(...)` is parsed,
not computed.

## Prompt Strategy

The current prompt is intentionally opinionated: every RLM, including child RLMs,
should act as an orchestrator.

The prompt emphasizes:

- inspect the context before committing to an approach
- decompose the task into independent sub-problems
- delegate semantic analysis to `llm_query*` or deeper iterative work to
  `rlm_query*`
- ask subcalls for evidence and `NOT_FOUND` rather than guesses
- verify returned claims before finalizing
- synthesize only evidence that was actually observed
- use one REPL block per turn and observe before finalizing

The depth-1 trace-generation prompt removes `rlm_query*` from the tool surface
and strengthens the instruction that the teacher should not solve everything
itself. This was added after early GLM-5 trace experiments showed that the root
model often avoided subcalls and solved with direct REPL logic.

Prompt definitions live in:

```text
environments/rlm_rlvr/rlm_rlvr/prompt_variants.py
```

## Reward Design

The reward path has two modes.

### Static Mode

`efficiency_penalty_mode = "static_per_1k"` preserves the old behavior:

```text
reward = max(0, correctness - efficiency_penalty_coef * total_tokens / 1000)
```

Incorrect or empty answers remain `0`.

This mode is still useful for compatibility and pure eval. Active eval configs
set:

```toml
efficiency_penalty_mode = "static_per_1k"
efficiency_penalty_coef = 0.0
```

so eval reward remains interpretable as correctness.

### Adaptive Group Mode

Active training configs now use:

```toml
efficiency_penalty_mode = "adaptive_group"
adaptive_efficiency_beta_max = 0.15
adaptive_efficiency_gamma = 1.0
adaptive_efficiency_solve_rate_floor = 0.25
adaptive_efficiency_cost_basis = "total_tokens"
efficiency_penalty_applies_to = "all_rollouts"
reward_clip_min = -0.5
reward_clip_max = 1.0
```

For a GRPO group:

```text
s = mean(correct_i)
beta = 0                                  if s <= 0.25
beta = beta_max * ((s - 0.25) / 0.75)^gamma otherwise
```

The original adaptive implementation penalized only correct rollouts. Current
full-FT and later LoRA configs use `efficiency_penalty_applies_to =
"all_rollouts"` so expensive wrong behavior is worse than cheap wrong behavior
when the group has some solvability signal:

```text
correct rollout reward = 1 - terminal_penalty - beta * normalized_cost
wrong rollout reward = 0 - beta * normalized_cost
reward = clip(reward, -0.5, 1.0)
```

`normalized_cost` is min-max normalized within the same prompt group. In
`correct_only` mode it is computed over correct rollouts only; in
`all_rollouts` mode it is computed across the whole group. Solve rate and online
difficulty filtering still use binary correctness, not shaped reward. If
`s <= adaptive_efficiency_solve_rate_floor`, beta is zero, so all-wrong groups
are not trained to prefer short wrong answers.

Finalization penalties are separate from cost:

```toml
max_turn_penalty_enabled = true
max_turn_penalty = 0.25
missing_final_at_max_turn_zero_reward = true
```

If the rollout reaches the forced-finalize turn and still does not produce a
formal `FINAL(...)`/`FINAL_VAR(...)`, correctness is forced to zero. If the
rollout only produces a correct formal final after the forced-finalize prompt,
it keeps correctness credit but subtracts the max-turn penalty.

This implements the current thesis hypothesis for cost pressure: hard prompts
with all-zero solve rate should not receive cheap-wrong pressure, mixed groups
should learn correctness while making expensive wrong behavior worse than
ordinary wrong behavior, and all-correct groups should become useful for cost
compression.

## Token And Trace Accounting

Each rollout records flattened `rlm_segments`. Segments include:

- root turns
- recursive child RLM turns
- finalize turns
- plain LLM subcalls

Trainability is explicit:

- `is_trainable_rlm_turn = true`: root, recursive, and finalize turns
- `is_trainable_rlm_turn = false`: plain `llm_query*` subcalls

Token accounting prefers explicit API usage fields for external subcalls:

- OpenAI-compatible usage: `usage.prompt_tokens` and `usage.completion_tokens`
- Vertex usage: `usage_metadata.prompt_token_count`,
  `total_token_count`, `candidates_token_count`, and `thoughts_token_count`
- Qwen tokenizer-derived IDs/counts remain the fallback

The reason is important for analysis: external subcalls are not trainable
samples, but their token counts are still cost and trace data.

## API Providers

The provider path changed during the project:

1. Initial local-only setup: all root, recursive, and plain subcalls used local
   GPUs. This slowed training because teacher-style subcalls competed with the
   trainable rollout model.
2. OpenRouter/OpenAI-compatible plain subcalls: plain `llm_query*` was moved off
   GPU to `openai/gpt-5.4-mini`, keeping root/recursive RLM local.
3. Vertex Gemini refactor: both plain LLM subcalls and semantic judge moved to
   Vertex through `google-genai`, with `global` location for Gemini 3.
4. Retry hardening: judge and subcall paths now retry 429/5xx/resource-exhausted
   failures. Vertex plain subcalls also retry empty responses.

## Trace Generation And SFT Attempts

The trace pipeline was built to create supervised warmup data before RL. It is
still valuable for analysis and future distillation, but SFT is no longer the
main training path for this thesis.

Initial idea:

- use the `sft_traces` split of `lsteno/BEEG-agents`
- generate full RLM trajectories with a strong teacher
- judge correctness quickly
- export only trainable RLM turns to SFT rows
- then SFT the base model before RL

Important experiments:

- GLM-5 via Prime Inference was tested first. It often avoided subcalls, even
  with a delegation-heavy prompt, so it was not a good teacher for decomposition.
- GPT-5.5 showed better decomposition on small hard/mixed probes.
- GPT-5.4 + Vertex Flash-Lite became the main cost/quality tradeoff for the
  first full 302-example SFT split.
- GPT-5.5 was used as an automatic retry teacher for GPT-5.4 failures.
- Claude Opus 4.7 and Qwen3 Coder Next were tested on remaining not-good traces.
  Qwen3 Coder Next recovered a small additional set; Claude was weak in that
  retry slice.

SFT was tried in two forms:

1. one full multi-turn conversation row per trace
2. one row per root RLM turn, matching the paper more closely:

```text
input  = full history up to this root decision point
target = next root action/finalization
```

Both approaches taught some surface protocol but did not produce a reliable eval
improvement over the base model. The likely causes were limited data volume,
teacher/deployment distribution mismatch, repeated early boilerplate, and a
base model that can imitate shallow REPL protocol without learning robust
delegation.

The first combined good set used this criterion:

1. no runtime error
2. exact match or `judge_score == 1`
3. at least one plain LLM subcall

## Why The Major Changes Happened

| Change | Why |
| --- | --- |
| Local REPL with `context` variable | RLMs need a persistent stateful workspace for structured inspection, counting, extraction, and verification |
| `llm_query` and `rlm_query` tools | The thesis is about orchestration, so the model needs a tool surface for delegating semantic work and deeper sub-problems |
| Sanjaya orchestrator prompt | Early models underused delegation; the prompt now explicitly frames every depth as orchestrator/delegate/verify/synthesize |
| Trace provenance and trainability flags | SFT/RL should train only on RLM-owned turns, not tool outputs or plain external subcalls |
| Explicit token usage fields | API subcalls often do not provide trainable token IDs, but their native usage metadata is better cost data than tokenizer guesses |
| API-backed plain subcalls | Offload subcall inference cost so local GPUs train the policy instead of serving teacher-style helper calls |
| Vertex provider | Needed first-class Gemini usage metadata, async support, and reliable judge/subcall routing without OpenRouter-specific assumptions |
| Judge retries | Vertex 429/5xx/auth transient failures otherwise caused noisy zero rewards and wasted rollouts |
| Empty subcall retries | Gemini occasionally returns empty text; retrying prevents bad traces and bad training signals |
| Subcall budgets and timeouts | Some traces over-delegated or hung; budgets keep rollout cost bounded and timeouts protect training steps |
| Worker-level recovery | A timed-out rollout can otherwise leave an env worker stuck on abandoned work; managed workers can be quarantined/restarted by generation |
| Attempt logging | Per-rollout JSONL logs record source ID, worker ID, start/end, true worker runtime, scheduler lag, timeout/reschedule/drop state, and token/subcall stats |
| Background group scoring | Deferred judge/adaptive scoring used to block the scheduler hot path; moving group scoring to bounded background tasks keeps vLLM fed |
| Bounded async scheduling | Unbounded speculative rollout carryover wasted work; current scheduling caps inflight work, accepts one-step carryover, and discards stale completions |
| Hard cooldown instead of permanent hard pool | All-zero groups are filtered from the current update but return after a short cooldown, so hard prompts can become learnable later |
| Process workers for trace generation | The local REPL mutates process-global cwd/stdout; processes avoid thread-safety bugs while still parallelizing generation |
| Curated SFT trace layer | Raw traces contain useful behavior plus protocol noise; curation preserves decomposition while removing bad finalization patterns |
| Adaptive cost penalty | Static token penalties pressure hard prompts too early. Adaptive group shaping uses prompt solve rate; current runs can penalize cost for wrong rollouts only when the group has some correctness signal |
| Max-turn finalization penalty | Bare repeated answers at the turn cap were sometimes rewarded by judge fallback; missing formal final at max turn now forces correctness to zero |
| NCCL full-model broadcast | Full FT needs fast whole-weight sync from trainer to vLLM. NCCL avoids writing/reloading a 4B checkpoint every step |

## Research Notes For Thesis Writing

The most important empirical observations so far:

- Stronger root models differ a lot in delegation behavior. GLM-5 often solved
  with direct REPL logic and avoided subcalls; GPT-5.4/GPT-5.5 were more likely
  to produce useful delegation traces under the current prompt.
- Subcalls help only when prompts are focused and evidence-seeking. Broad
  "analyze this" subcalls often produce noise, wrong line numbers, or fenced JSON
  artifacts.
- Over-delegation is real. Some correct traces used many subcalls. For SFT this
  is acceptable as a first pass because it teaches delegation; RL and adaptive
  cost shaping are intended to compress inefficient traces later.
- Finalization protocol is a major source of otherwise avoidable trace noise.
  Many correct trajectories had the right answer but used bare answers,
  `FINAL(json.dumps(...))`, or `FINAL(...)` in the wrong place.
- Dataset difficulty matters. Some tasks are easy to solve with direct Python
  over `context`; these may not teach decomposition unless the prompt and data
  selection enforce or reward delegation.
- Judge correctness is useful for filtering, but exact match and manual audits
  remain important for line-number/code-location tasks where gold labels may
  contain off-by-one or formatting ambiguity.
- For RLVR, cost pressure should be solve-rate aware. A global token penalty can
  discourage hard-prompt exploration, while all-correct groups are good places to
  optimize cost.
- SFT was not enough in this setup. It taught some formatting/protocol but did
  not reliably improve deployed RLM behavior, even when exported per root turn.
  RL is now treated as the main mechanism for learning when to delegate, when to
  stop, and how much computation to spend.
- LoRA rank/LR sweeps showed real failure modes: high-LR LoRA can collapse into
  one useless subcall, while other runs learn long local REPL loops. Reward
  shaping and observability were updated specifically to make these behaviors
  visible and worse than ordinary wrong answers.
- Full-parameter RL has a different bottleneck from LoRA. Adapter sync is cheap;
  full-weight sync is not. NCCL broadcast and independent vLLM servers are
  required for practical no-LoRA RL on the current 8x A100 pods.
- Attempt timing must distinguish worker runtime from scheduler consumption lag.
  Earlier 600-second p99 attempt metrics were often completed rollouts waiting
  to be consumed, not true 600-second worker executions.

## Known Limitations

- Remote/sandboxed REPL backends are not implemented; the environment currently
  supports only the local REPL.
- The current adaptive cost basis supports `total_tokens` only.
- Online difficulty filtering should be interpreted through binary correctness,
  not shaped reward. All-zero groups are filtered/cooled down; all-correct groups
  are kept in current runs so adaptive cost compression still has signal.
- Some output directories contain local experiment artifacts and W&B metadata;
  treat them as research logs, not polished release assets.
- The SFT trace corpus is still useful as an analysis/distillation asset, but
  the first two SFT attempts were not strong enough to use as the main training
  path.
- Full-FT configs are still experimental. The current `5e-6` run was chosen
  because `1e-6` under-moved the policy; if KL spikes or entropy collapses, the
  next conservative fallback is `3e-6` or stronger KL.
